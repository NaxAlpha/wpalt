# Structured editing with ProseMirror

Decision: 2026-10-02, M3.5. Implement the approved integrated authoring milestone with a bundled ProseMirror engine and a server-validated version-1 document envelope. No Node process, external font, account activation or authoring service is required at runtime.

The editor uses immutable state and transactions for selection, input, paste and history. Document-start/end keymaps use public selection transactions, avoiding races with delayed native caret reconciliation after composition. Toolbar operations synchronize pending native selection through the engine’s public DOM-position and selection APIs; mouse/touch block movement uses pointer capture and the same document transactions. We avoid maintaining an independent DOM-to-text engine. The exact dependency graph is locked in frontend/package-lock.json; the build includes MIT notices in the embedded bundle. This adds client bytes, measured in the milestone evidence, in exchange for mature input and history behavior. The server independently validates the document; client validation is not a security boundary.

Canonical `document` and `published_document` contain `{version:1,root:<ProseMirror tree>}`. Public rendering escapes text and attributes using Maud, accepts only supported nodes/marks/attributes, validates HTTP(S)/local links, and bounds serialized bytes, text, node count, depth and table dimensions. Basic tables do not support merged cells or arbitrary column widths. Images are served through existing visibility checks; wpalt never fetches imported external images. The site's existing self-only image CSP remains in effect.

`body` and `published_body` remain search/export/template text projections. Explicit Markdown API input remains an import capability, not a second public-rendering path. Original Markdown and legacy composition source are preserved during the one-off migration and in retained revisions. Structured edits derive the projection and clear imported composition provenance. Public rendering always reads the canonical tree; ordinary documents never use an old-format renderer. Theme-authored literal Markdown remains a separate theme capability. Markdown exports are a readable projection, not a lossless substitute for JSON documents; current-format backups retain the full tree.

Schema 4 converts both working/live snapshots and retained revisions in bounded keyset batches inside one transaction. A conversion error aborts the migration with source data intact; operators correct unsupported input using the old binary or restore their independent pre-upgrade backup. Backup v4 accepts current document trees and rejects invalid grammar before writing. Older archives are restored with their matching binary, followed by the one-off database upgrade; no legacy archive parser is retained.

Browser recovery is local to this browser, account and editor URL. It requires an explicit restore/discard choice and never silently replaces server work. Recovery is convenience, not offline synchronization or a backup. Server saves retain optimistic versions; conflicts preserve browser text and require reload/review. Browser storage may be unavailable and cannot guarantee recovery after every crash. No private draft is logged.

Primary guidance checked 2026-10-02: https://prosemirror.net/docs/guide/ and https://prosemirror.net/docs/ref/ (retrieved directly because the research browser returned 403), https://www.w3.org/TR/input-events-2/ (01 May 2026 Working Draft, not a Recommendation), and existing WCAG 2.2 design contracts. The Notion interaction reference informs familiar writing interactions, not a claim of Notion feature parity. M9 retains broader browser/device and assistive-technology release validation.

Public listing/search now materializes at most 21 lightweight candidate identities before retrieving page text and fields. A SQLite partial index covers indexable identity/language/date lookups, so JSON SEO predicates do not require reading every wide structured post row during common ranking. PostgreSQL retains its GIN search index and uses the same bounded candidate stage. This deliberate materialization fence trades a tiny bounded intermediate relation and one extra SQLite index for avoiding large payload reads before pagination. Noindex, language, taxonomy and cursor filters remain inside the candidate stage. A save writes content, metadata and both snapshots in one optimistic INSERT/UPDATE, avoiding a second wide-row rewrite. Measurements and query-plan evidence are recorded alongside the storage increase from canonical documents.

SQL guidance reviewed 2026-10-02: [SQLite materialization hints](https://www.sqlite.org/lang_with.html#materialization_hints), [SQLite partial indexes](https://www.sqlite.org/partialindex.html), and [PostgreSQL WITH materialization](https://www.postgresql.org/docs/current/queries-with.html). SQLite recommends leaving materialization to the planner unless there is a compelling reason; wide-row ranking is the measured reason here. PostgreSQL 17 is the CI-tested engine; the current documentation describes PostgreSQL 18.
