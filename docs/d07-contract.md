## End-user outcome
An owner uses the existing Studio model editor to declare named typed entities and bind their properties to the same typed content fields that editors publish. An article can explicitly identify public authors/publisher and factual images/dates. An organization can publish multiple separate location records with real address, contact, coordinates and opening hours, related by existing native relationships. Readers see the exact factual values that the shared head emits as JSON-LD; private/draft/member/revoked related records do not become public facts. Owners can inspect dated vocabulary and selected Google guidance warnings without an indexing or rich-result promise.

## Authority and grammar
Optional per-model `structured` declaration, omitted from serialization when absent. Known named entities have known Schema.org types and known properties. Bind only declared typed fields, named local entity identities, existing relationship identities, admitted local images and factual publication attributes. No arbitrary scripts/raw JSON-LD, network context processing, private account-name/email inference, copied product price/availability authority or fabricated publication-modification date. Published values and existing access checks stay authoritative; model configuration remains exact-version administrative configuration. The full offline vocabulary enables supported custom declarations, with explicit pending/deprecated status. Domain/range admission is a documented bounded native policy, not a claim of complete open-world Schema.org or JSON-LD processing.

## Composition and privacy
Reuse the registry, relationship and media batches already loaded by the shared theme context; disabled/absent declarations add zero queries and no vocabulary parsing. Graph/fact projection is constructed once and passed to head/body, with a shared readable facts surface across themes. Reconcile existing basic Article/WebPage output instead of emitting contradictory implicit nodes. Resolve related facts only through current published/unrestricted identities. Fixed named entity references may be cyclic but each identity is emitted once under aggregate budgets; recursive expansion cannot evade node/property/depth/output ceilings. Values displayed and emitted share one projection. No root draft head JSON-LD.

## Admission detail — functional implementation
Explicit field Text/URL representations follow Schema.org's documented pragmatic fallback; remaining scalar datatypes and typed entity/enumeration ranges must fit declared fields and vocabulary hints. Publication convenience attributes remain semantically typed. Editorial properties cannot copy native catalog price, priceCurrency, lowPrice/highPrice, availability, inventoryLevel, offers, priceSpecification or eligibleQuantity; authoritative commerce enrichment remains D16. A generic vocabulary builder is not a claim of a complete commerce/provider schema integration. Native no-JavaScript authoring keeps its explicit JSON field fallback; custom content models are selectable server-side, while the default enhanced editor provides named field controls.

## Integrated visible identity review
Multiple related records may reuse entity names. HTML anchors therefore derive from the complete graph identity, rather than its fragment suffix; relationship links resolve to the corresponding facts on the current page. The pre-fix browser reproduction emits six facts sections with only four unique IDs. The regression checks unique DOM IDs and exactly one visible target for every relationship link. JSON-LD canonical identities remain unchanged.
