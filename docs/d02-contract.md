# D02 — Reviewed publication and editorial assignments

Date: 2026-10-06 (Tokyo). Active autonomous package after the verified D01 delivery. Implementation has not yet passed its delivery gates. This is a separate PR following D01 PR #17, merged on 2026-10-07 as `051d319`. The owner authorizes merge when current-source delivery gates pass.

## End-user outcome

An owner enables reviewed publication for a content model. An editor writes and requests review from another eligible editor/administrator. The assigned reviewer inspects the exact working copy, approves or requests changes with a private note. An authorized publisher can publish or schedule the approved material; changed work, stale assignments/authority and changed review policy require a new review. A local editorial queue brings assignments, notes and status into the existing writing experience without a provider account.

The current editor role has broad content/media authority; do not label it a restricted author/contributor. General custom roles, ownership-restricted contributors and capability policy across all modules remain D13. D02 adds explicit assigned-reviewer authority and publication policy to the current editor/admin roles. It does not pretend that an editor cannot read other editors' drafts. No paid-plugin executable parity is assumed.

## Functional-first steps and verifiable gates

1. Add a declarative per-model review requirement, default off for existing definitions. Keep editorial state relational and separate from immutable content revisions: current content version/last editor, requested reviewer, private decisions and bounded history. Index the current assignment/status projection. No registry lookup or workflow query is added to ordinary public reads.
2. Require current sessions/roles under the shared mutation boundary for each transition. Reject unassigned and self approval, stale workflow/content versions, invalid accounts and integration-token approval/publication. Request, reassignment, decision and withdrawal use compare-and-swap versions and bounded plain text. Never accept submitted approval state or actor IDs as authority.
3. Bind approval to canonical meaningful content, including normalized document/title/slug, typed fields/blocks, language/group, SEO and classification, plus the relevant current definition/policy. A matching version alone is insufficient: a publish request can carry altered values. Saving/restoring material invalidates approval; old content cannot invent a last editor, and must be saved through the current workflow before entering review.
4. Scheduling freezes the exact reviewed material. Editing scheduled work or losing current approval/policy/reviewer authority cancels the pending promotion and preserves any earlier live snapshot. The worker must not promote later unreviewed drafts. Ordinary models keep their existing deliberate publication behavior.
5. Integrate review controls and private notes into the current editor, add a paginated assignment/review queue and local actionable notifications. Use the existing cardless primitives, clear waiting/error states, native form/keyboard semantics and responsive measurements. Optional email is explicit owner configuration through existing durable communications; local review must work without it, and transport claims require evidence.
6. Preserve state/history through native backup/fresh recovery, and validate actors, versions, states, sizes and graph relationships before target writes. A new table graph receives a native schema-17 fence and portable v13. Existing v12 archives use an explicit offline conversion boundary; pre-change recovery retains original bytes for the old executable. No ordinary runtime/restore fallback or silent legacy rewrite. Document supported source schemas and a converter retirement path.
7. Verify connected writer/reviewer/publication journeys, same-version forged content, stale/parallel approvals, denied actors, role revocation, schedule edits, restored revisions, private queue/notes and fresh recovery on real SQLite/PostgreSQL. Use populated queue pagination and explain its plans/work budget. Extend readable high-level clusters rather than mechanical field permutations. Verify each working step, then optimize security, performance and UX together.
8. Deliver a separate reviewable PR with current-source strict lint, formatting, guidance checks, meaningful Rust/CLI/browser tests and independent clean-artifact verification. Preserve the rest of the backlog, report limits honestly and continue autonomous work that does not require owner accounts/access/decisions.
