# D03 — Language workspace and owner-localized administration

Date: 2026-10-07 (Tokyo). Prepared while D02 delivery gates run; implementation begins after its verified base. Scope derives from D03/F008–F011, not a replacement of remaining language breadth.

## End-user system

An owner manages configured site languages and administrators choose a supported interface language independently of the content they edit. Writers view related language variants side by side, create a deliberate unscheduled translation draft, and explicitly synchronize selected shared values with source/target version checks. Existing publication, access rules and D02 review remain authoritative. A local model may propose translations for canonical long documents without replacing links, protected resources, block identities or the author's work silently; review and deliberate publication remain necessary.

## Functional steps and delivery evidence

1. Establish a versioned local message catalog and explicit interface-language preference, independent of public language. Scope each supported translation honestly; fallback preserves usable English rather than claiming complete translation. Use stable message IDs, parameter escaping, plural-aware messages and locale-aware formatting. Catalog loading is bounded and bundled/offline; no vendor account or runtime remote translations. Inventory missing messages and supported languages; tests target connected task/error states, not one mechanical test per string.
2. Add a language workspace connected to the editor: bounded grouped variant lookup, clear source/target status and publication/review state, configured language/direction labels, preview links and edit comparison. Declare real content language and direction separately; isolate bidirectional identifiers, URLs and mixed-direction user content. Preserve keyboard, reflow, focus and design primitives in LTR/RTL and expanded labels.
3. Implement browser/API draft duplication and selected synchronization through current-session authority and the shared mutation boundary. Do not call the CLI workflow's fabricated stopped-site owner from HTTP. Recheck exact source/target versions, group/kind/language and access restrictions before commit. New protected targets need explicit access provisioning; do not turn private source material into an unprotected draft. Never change translated text, SEO, classification, publication or access without the deliberately selected operation. Edits invalidate editorial approval normally.
4. Extend local proposals from short title/body samples to bounded canonical document text segments. Preserve structural IDs/types, attributes, URLs, media/form identities and non-translatable code. Version source, locale/model and complete proposal; partial failure remains recoverable/reviewable and cannot publish. Keep outside providers optional and account-bound; local jobs cannot claim translation quality from valid JSON alone.
5. Verify meaningful English/French/Japanese/RTL workflows, missing-catalog fallback, unsafe placeholders, narrow/long labels, mixed-direction text, concurrency, protected duplication, source changes and denied actors. Run representative long-document structural/fact-preservation evaluation with an actual installed local model; report failures and human editing needs. Do not infer universal language quality from small synthetic samples.
6. Preserve preferences and meaningful proposals through fresh SQLite/PostgreSQL recovery and native migration when persistence changes. Record bounded query/work plans, request/memory/disk observations and relevant security/UX limits. Run cumulative tests and exact-source CI, independently verify the clean artifact, then deliver and merge a ready PR under the owner's 2026-10-07 authorization.

## Primary guidance checked for preparation

[W3C language declarations](https://www.w3.org/International/questions/qa-html-language-declarations.html) and [language authoring guidance](https://www.w3.org/International/docs/bp-html-lang/) distinguish actual page/content language from direction. [WordPress installation language](https://developer.wordpress.org/advanced-administration/before-install/in-your-language/) and [Site Health documentation](https://wordpress.org/documentation/article/site-health-screen/) show site/user language as separate concepts. [Polylang duplication](https://polylang.pro/documentation/support/guides/duplicating-content-across-post-translations/) and [metadata synchronization](https://polylang.pro/documentation/support/guides/synchronize-metadatas-between-translations/) are vendor reference semantics; premium behavior is documentation-only until access exists. Refresh formal guidance mappings before affected implementation; no universal plugin parity claim.

## Retained scope

Complete professional translations of every supported language, arbitrary third-party catalogs, provider certification and unrestricted automatic translation accuracy remain evidence-dependent. Real-time collaboration/Notion databases remain a separate product decision. Record bounded initial language coverage and missing useful breadth rather than presenting a shell preference as completed administration localization.
