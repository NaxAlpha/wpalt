# D13 preparation — 2026-10-13

Read-only assessment while final D12 delivery runs. No application change yet.

Current fixed roles live in users.role with a database CHECK. Session.can_edit/can_moderate/is_admin and durable auth::current_editor cover different entry points. Membership::staff is reused by commerce::owner, so learning and commerce delegation must be separated. Direct protected reads and course lists independently check hard-coded editor/owner roles. Editorial reviewer selection and scheduled participant checks also use fixed roles; changing menu rendering alone would leave inconsistent authority. External credentials currently bind original owner/editor roles and password fingerprint, independently of sessions. Password, passkey and provider sign-in construct Session independently, and stopped CLI actors do too.

Candidate native design: owner-managed finite permission registry; versioned custom role records and explicit assignment relation, leaving users.role constrained to built-ins. No custom role may manufacture the immutable owner authority or grant external bearer/recovery keys. Join current enabled grants into session resolution, require fresh subject/session/grant state after mutation locking, and invalidate all affected sessions/credentials on role/assignment change. Missing/deleted/unknown capability denies. Preserve entitlement/resource guards unless a separately visible privileged-read capability was deliberately granted. Edition/reviewer/worker eligibility must use the same durable registry, not cached role text. A permission plan must enumerate every shared-editor/admin callsite before implementation; business/forms/audience/mail, themes/discovery, learning and commerce need separated checks where delegated.

Owner UI: create/edit/suspend a named role with plainly described finite rights, inspect assignment count, assign through People & access, preserve the last owner, refuse deleting an assigned role or use explicit exact review. Stopped CLI uses the same registry/validation. Private export/restore must validate canonical grants and fresh stopped upgrade; current-schema restore only, explicit conversion from authentic original D12.

Verification clusters: real SQLite/required PostgreSQL role assignment, direct route/API/download/private disclosure boundaries, stale actors and concurrent change/revocation with one winning exact version, scheduled/editorial/integration narrowing, meaningful fresh recovery/tampered privilege refusal, readable failure/keyboard/narrow UI, indexed query and finite-count observations. Existing cumulative seven gates and downloaded final artifact/main/public checks remain required.

Primary sources checked 2026-10-13: https://developer.wordpress.org/plugins/users/roles-and-capabilities/ ; https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html ; https://www.postgresql.org/docs/17/explicit-locking.html . These support capability-oriented checks, least privilege/default deny/current request checks and transaction lock reasoning. The exact finite registry and immutable owner are wpalt product decisions, not WordPress runtime compatibility.
