# Business workflows — M4 development

M4 is in progress in PR #8. The current usable slice provides form creation, a basic visual designer, publication, public collection and protected response viewing. It does not yet deliver the complete business/audience contract.

When `business_enabled = true` (default), editors and administrators open **Forms**, create a titled form, edit labels and text/number/checkbox inputs, mark required fields, arrange up to eight ordered steps and add conditions or numeric sum/product calculations from earlier fields. Save the working copy, then publish when ready. Publication preserves its reusable groups; later shared-schema edits do not reinterpret accepted responses. The published form is available at `/forms/<id>`. Responses are visible through **View responses** in the same admin workflow. Moderator accounts and unauthenticated visitors cannot read or edit private business state.

The basic designer currently creates primitive fields. The backend shared grammar also validates bounded object/group/repeater definitions, but their complete visual authoring/visitor widgets remain part of the next form step. Embedded content/theme blocks, uploads, signatures, choice/survey controls, pricing rules, partial/offline recovery, workflow actions, search/export/notes/assignments and pagination beyond the recent-40 views remain pending. Arithmetic currently uses finite floating-point values; it is not a payment or exact-currency engine. Audience/communications/engagement remain required M4 work, not removed scope.

The response limit defaults to 10,000 accepted entries per form, across its publications, and may be configured between 1 and 1,000,000 in the designer. Concurrent submissions cannot exceed the limit. Repeating an accepted UUID/payload returns the same entry without consuming another slot; changing the payload for that identifier conflicts. New responses using a stale public version are rejected. This storage bound is not a complete spam or identity-verification system; additional form abuse controls are pending.

Definitions allow at most 32 top-level fields, eight ordered steps, the shared depth/width/expanded-node budgets, and earlier-field rule dependencies. Collection requests are capped at 128 KiB, individual strings at 8,000 bytes and repeaters by their declared limits (at most 50). Hidden values are discarded and calculated values recomputed on the server before storage. Partial rule evaluation remains typed but is not yet a public draft-recovery endpoint.

The designer and public form need JavaScript, served from the same self-contained executable. No external editor/validation service or wpalt account is required. Failed requests preserve the values in the currently open page; durable device/server draft recovery remains pending. Debug records include request correlation, form/entry identifiers and publication versions, never form payloads.

Set `business_enabled = false` in the TOML configuration, or `WPALT_BUSINESS_ENABLED=false`, and restart to remove business routes, navigation and the form asset. Stored data remains available for a later re-enable and for backups. Analytics capture and mail workers are not implemented in this slice. See [operations](operations.md#m4-development-upgrade-in-progress) for schema-5/backup-v5 recovery. Schema 5 is an evolving pre-adoption branch format: disposable data made by intermediate M4 development commits may require reset/reseed; meaningful M3.5 schema-4 data follows the documented upgrade/independent-backup path.
