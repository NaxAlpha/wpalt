# Owner-operated resilience — M7 implementation guide

Implementation in progress. The recovery, caching, authentication, inspection and local-rule scopes described here exist; this does not declare M7 or its broad parity families complete.

## Recovery keys and portable packages

`wpalt recovery-key /secure/recovery.key` creates a private 256-bit random recovery key without opening a site database. Copy that key independently offline. This is a key, not a password. Loss of all copies makes encrypted packages unrecoverable. Do not store it inside backup destinations.

`wpalt --config site.toml backup /independent/site.wpbackup --key-file /secure/recovery.key` captures the existing consistent logical database/media/private-attachment snapshot and authenticates/encrypts it using ring ChaCha20-Poly1305 with a fresh random 96-bit nonce and authenticated format metadata. The package has a versioned binary envelope. Existing plaintext manual backup remains explicit. Keys are never accepted as command-line values or embedded in packages.

With the original host unavailable, install the executable on a fresh host, configure an empty SQLite/PostgreSQL database and new data directory, bring the independently held key/package, then run `wpalt --config fresh.toml restore /independent/site.wpbackup --key-file /secure/recovery.key`. Authentication and the existing whole-graph validation precede database writes. Non-empty destinations are rejected. Existing sessions are not recovered. External credentials and host configuration remain owner-managed and must be recreated securely; the archive does not replace a deployment configuration inventory.

## Managed schedules, copies and retention

Configure `[recovery]` with `enabled=true`, private `key_file`, one to eight existing absolute `destinations`, `interval_seconds` (60 seconds to 30 days), and `retain` (1–365). Run `wpalt recovery-run` offline, or use Operations → Create encrypted recovery copies while serving. `wpalt recovery-status` and Operations display durable last attempt, last complete set and each destination's verified/failed/pending status. The server scheduler triggers due captures. Settings currently require restart; arbitrary destination paths cannot be submitted by browser users.

A destination can be a mounted independently managed NAS/disk/secondary-host filesystem. This does not implement SFTP credentials or prove physical independence. Missing directories are not recreated: a lost mount must not become an apparently successful origin-disk backup. Configure monitoring/mount policy and test actual source-host loss. A pending status after restart indicates an interrupted attempt; no partial file is considered complete. Retry waits the configured interval to bound repeated failure work, or the owner can retry explicitly.

Copies are published as private, fsynced, no-overwrite packages through temporary files and then read back/authenticated. Retention follows verified copying, preserves the current package, touches only recognized regular package filenames, and refuses to remove a damaged or wrong-key old package. Unrelated files and partials are retained for operator inspection. Directory size is bounded during enumeration. Failed destinations leave the successful copies intact and remain visibly failed; CLI returns failure if any copy is incomplete. Filesystem/hardware durability still depends on the storage's actual sync and hard-link semantics. Unsupported destinations fail rather than silently reducing guarantees.

## Bounded public cache

Configure `[cache]` with `enabled=true`, `max_bytes`, `max_entries`, and `ttl_seconds`. It stores only successful anonymous publication/listing/search/sitemap/public-content projection responses with known bounded bodies, without cookies/Authorization/Range or Set-Cookie/private/no-store output. Query and language URLs are distinct. Private pages, account flows, member media, forms and commerce are excluded. Response-size budget failures are not silently truncated.

Shared application mutation guards advance the cache generation at entry and exit, including failed mutations. Cacheable rendering holds the shared read boundary to prevent an intervening committed access change between rendering and insertion. Hits receive fresh outer request/security headers; cached request IDs are removed. Entries have TTL and total-byte/entry bounds with oldest-first eviction. `x-wpalt-cache` identifies hit/miss. Restart empties cache. This is single-process application cache, not distributed invalidation or a CDN, and operator SQL outside wpalt is not an automatically observed mutation. Native database changes require restart or an explicit application invalidation boundary. Owner-triggered bounded preload and gzip/asset-header controls are described below. Distributed invalidation remains M9.

## Local request protections

Configure `[protection]` with `enabled`, literal `denied_prefixes`, exact `denied_peers`, `requests_per_window` and `window_seconds`. Matching path prefixes use segment boundaries, not arbitrary regex code. Rate counters key the actual TCP peer, not X-Forwarded-For. Behind a proxy, this means a shared proxy counter; configure protections at that outer proxy rather than assuming forwarded user identity. Health reads bypass the rate counter but not explicit deny rules. Active peer counter storage is bounded to 4,096; exhaustion fails closed instead of evicting active counters and granting fresh budgets. Request concurrency, timeouts and body limits remain in force. This local protection is not edge DDoS absorption. Changes require restart; keep the config/CLI recovery path available if an owner deliberately blocks their administration routes.

Draft milestone delivery: https://github.com/NaxAlpha/wpalt/pull/13. Not ready for merge.

## Native image derivatives

`/media/{id}/resize/{width}` produces WebP at one of 320/640/1280/1920 pixels without enlarging originals. The same current role/entitlement checks as original media run before processing. Output is no-store, never a private-file cache bypass. Native blocking workers hold the bounded media semaphore throughout decoding/encoding; source bytes, pixels and decode allocations are bounded. PNG/JPEG/WebP are accepted; GIF derivatives are explicitly rejected to avoid silently removing animation. On-demand processing currently avoids persisted derivative recovery/cleanup complexity; AVIF, derivative reuse, video processing and richer authoring integration remain M7 work.

## Stored-file inventory scan

`wpalt integrity-scan` or Operations → Inspect stored-file integrity checks stored image/private attachment paths, regular-file metadata, byte counts and authoritative SHA-256. It does not remove or quarantine files. Work is bounded to 1,000 rows per inventory and 64 MiB total; a limited result explicitly fails the CLI success gate, rather than certifying unexamined files. Browser access requires administrator authority and CSRF. Keyset continuation and explicitly labeled pattern review are described below; durable scan history remains outstanding.

Image dimensions are strict decoder limits. The image library documents allocation limits as best-effort; the configured 64 MiB decode allowance is not a guaranteed process-memory ceiling. Worker admission also bounds simultaneous decoding.

## Privileged HTTP action history

Native `/admin` and `/api/admin` writes persist a private journal intent before dispatch and response status afterward. Failure to persist intent stops dispatch. If an action committed but its outcome cannot be written, the response is preserved with `x-wpalt-audit: outcome-write-failed` and an error diagnostic; a misleading failure must not encourage blind replay. Interrupted intents explicitly lack a paired outcome. Matched route patterns, request correlation, current local actor ID, timestamp and status are recorded; bodies, query values, passwords, session/CSRF tokens and email addresses are excluded. Operations links the administrator-only recent history (200 records). Two bounded 1-MiB private files retain current/previous logs; archive externally for longer retention. Privileged offline command classes now record host-owner intent and success/failure outcomes through the same journal, without argv or paths; intent failure stops dispatch, and outcome-write failure preserves the command result with an explicit warning to inspect state before retry. Portable inspection/extraction and key generation remain independent file tools. The recent 200-record view spans both current and previous logs. This is an operational journal, not tamper-proof storage or a database transaction ledger; background scheduler cycles use the separate bounded history described below. Full/incremental logical archives now preserve the most recent 200 validated audit records. A fresh restore merges those records into the destination journal while preserving its own restore intent; inspection deduplicates records and shows the most recent timestamps. Archive longer history externally.

## Local account protection (introduced in native schema 12)

Account → Security supports locally generated six-digit TOTP (30-second steps), verified enrollment, transactional replay rejection and eight one-use recovery codes. Codes are shown only at confirmation; only their hashes persist. Enable/disable and passkey removal revoke other sessions. Password reauthentication is bounded and rate-limited. OIDC refuses accounts requiring the local factor, so it cannot bypass that factor. Keep host/database storage private: TOTP secrets must be available to the verifier and are sensitive backup data.

Passkeys use webauthn-rs 0.5.5 for origin, signature and user-verification validation. Challenges stay in bounded server memory for five minutes and are consumed once; registration is tied to the authenticated session and current password/factor. At most eight keys per account, globally unique credential IDs, transactional version/counter updates and current-account checks prevent stale concurrent sign-ins. Restart cancels pending ceremonies. Use HTTPS with a domain in production; use `http://localhost:PORT` for local evaluation, rather than an IP-address relying party. The real Chromium journey uses a virtual CTAP2 user-verified device; it is not a claim of every hardware authenticator's interoperability.

A host owner who loses factors can stop the server and run `wpalt auth-reset --email EMAIL`; this clears factors/passkeys/sessions and still requires the password afterward. Possession of application storage is already an administrator boundary. It is never a public recovery endpoint.

Schema 9/10/11 upgrades transactionally to 12, adding account factors/passkeys, the private data-request queue and durable clone mode. Current full archives are `wpalt-backup-v13`, preserving bounded recent operational history and validated data requests. Unreleased M7 v9/v10/v11 preview archives require their matching executable to restore, then upgrade and re-export; disposable preview fixtures may reset. For a meaningful M6 plaintext v8 archive, use `wpalt migrate-backup OLD NEW`; it verifies the old checksum, adds empty new tables and validates the complete current graph before writing a NEW private archive. Ordinary restore accepts only the current format; there is no legacy runtime. Encrypted old archives can be restored with their matching release before database upgrade and re-export.

## Incremental independent recovery

Set `incremental = true` under `[recovery]` to store encrypted 64 KiB chunks alongside each encrypted manifest. Object IDs are keyed HMACs; chunks authenticate independently and the reconstructed archive has an overall checksum. Every manifest represents a full independent point; no parent backup chain is required. Carry the package, its sibling `wpalt-objects` directory and the separately stored key to the recovery host. Chunk equality and approximate sizes remain visible to storage observers. This is application-snapshot deduplication, not PostgreSQL WAL point-in-time recovery.

Retention removes old packages only after the replacement is verified. Object pruning is deliberately explicit: stop all writers of that destination; `wpalt recovery-prune DESTINATION KEY_FILE` authenticates every retained point and prints bounded cleanup counts and a `plan` hash. Repeat with `--execute HASH` to remove only the currently unreferenced objects. A changed plan, damaged retained point, unsafe path or exceeded scan budget stops deletion. A destination shared by independent writing hosts is unsupported before M9.

`recovery-inspect INPUT [--key-file KEY]` validates a whole graph without opening a database or requiring an installed site. `recovery-file INPUT UUID NEW_OUTPUT [--key-file KEY]` extracts one validated image/private attachment into a new private file; it never injects rows into a live site. Both use the same bundled binary and configuration budgets. Restore still requires an empty target and the owning-process lock. Arbitrary selective financial/learning graph merge is unsupported and must not be inferred from file extraction.

Public caching now includes anonymous unprotected publication pages and public content projections, with the same mutation invalidation and cookie/authorization bypass. Protected publications are excluded even when a policy temporarily permits anonymous access. Browser publication responses remain no-store to honor revocation. Operations shows retained entries/bytes and provides an authenticated CSRF-protected purge. Compression remains gzip; arbitrary externally trusted geolocation/role variants are not supported.

## Bounded inspection and owner-page cookie worker

Integrity inspection supports keyset continuation with `next_image`/`next_attachment` cursors, including the literal `done` sentinel. The native admin screen offers Continue inspection; CLI accepts `--after-image` and `--after-attachment`. A batch has at most 1,000 rows per inventory and 64 MiB of file reads. Executable/PDF JavaScript patterns generate explicit owner-review warnings, separate from checksum failures. They can be false positives and do not certify malware absence. File hashing/pattern work uses bounded background workers; no scan deletes or modifies files.

The optional developer/owner worker `node scripts/cookie_scan.cjs ORIGIN NEW_PRIVATE_REPORT [PATH ...]` uses the locked Playwright browser to inspect up to 20 explicit same-origin pages. It records cookie attributes, storage key names and script paths before consent, after allowing local analytics and after withdrawal when those controls exist. Cookie/storage values and query tokens are omitted. Foreign requests are blocked and their origins reported, so this cannot assert what every third-party script would do when allowed. It never enables collection or changes server settings. Node/browser tools are declared optional inspection dependencies, not runtime dependencies of the CMS. The sampled-page result is evidence for review, not legal certification or a complete crawl of all runtime states.

The new passkey dependency activated `time` in the selected dependency graph. CI detected RUSTSEC-2026-0009 in 0.3.45; the lockfile now uses patched 0.3.47. No audit exception was added. Keep the Rust floor at 1.88 and re-run the selected-graph audit for future updates.

Public cache preload warms up to 20 recent unprotected publications under current read/mutation coordination, without outbound requests. Compression runs after cache lookup so gzip/identity share one uncompressed cached representation and negotiate independently. The byte budget accounts for body, keys, headers and entry metadata; it is not a process RSS ceiling. `[cache].gzip` controls gzip globally, while `asset_cache_seconds` controls mutable bundled asset URL freshness (default zero/revalidate; maximum one hour). Longer immutable caching awaits versioned asset URLs.

## Local submission abuse guard

Opt-in `[spam] enabled = true` protects public comments and form entries. `proof_bits` defaults to 12 and accepts 0–16; `max_links` defaults to 10 and accepts 1–100. Each challenge expires after ten minutes, is authenticated with a per-process secret, bound to its comment slug/form ID and consumed once under a mutex. Replay storage is capped at 4,096 unexpired proofs; a full budget fails closed. Restart invalidates outstanding challenges. Client work stops after fifteen seconds or 1,048,576 candidates, so failed work can be retried with a fresh challenge. HTTPS or a browser-trusted localhost origin is required for Web Crypto. Enabled comment submission needs JavaScript; disabled sites retain the native form path.

The hidden website trap and case-insensitive literal HTTP(S) link count provide basic policy friction. They do not classify all URLs, identify humans or provide shared spam reputation. Existing request limits, input validation and comment moderation remain active. No response contents, browser fingerprints or proof tokens are added to audit history.

Run `WPALT_SPAM_ONLY=1 PLAYWRIGHT_MODULE=... node scripts/browser_acceptance.cjs` for the real browser comment/form journey, and `cargo test local_abuse_guard` for destination binding, heuristics and racing replay admission on each configured real database. Current anti-automation guidance: [OWASP Bot Management](https://cheatsheetseries.owasp.org/cheatsheets/Bot_Management_and_Anti-Automation_Cheat_Sheet.html), checked 2026-10-04.

## Before an executable upgrade

Stop the site and run the **currently installed executable**: `wpalt --config site.toml upgrade-prepare /independent/upgrade-before-change.wpbackup --key-file /private/recovery.key`. It creates a new encrypted full snapshot, reads and decrypts it back, validates the complete graph, then prints a JSON receipt containing archive/executable SHA-256 identities, size, schema and recovery instructions. Save that receipt with the old executable and private config; store the key separately. Existing output files are never overwritten. Use a separately retained pathname outside scheduled-retention filenames. A nonzero exit is not upgrade approval. This command does not replace binaries or prove a host-independent restoration.

Before changing the executable, test the encrypted archive with the old executable in an empty database/data directory. Verify publishing, owner login, protected content and business/financial state. Preserve the old instance until the new instance is verified. If the new upgrade fails, stop it and restore with the retained old executable into an empty instance; do not point an old executable at migrated tables. Switch back only after verifying the restored instance. Account for writes accepted after the checkpoint explicitly: rollback cannot invent those writes or silently replay payments/deliveries.

## Native image delivery and reusable derivatives

The media library links WebP sizes (320/640/1280/1920) and AVIF (320/640/1280). AVIF uses the native Rust image 0.25.9 encoder at speed 10/quality 60 with one thread and at most two million output pixels. Originals are never enlarged. GIF, APNG and animated WebP stay on their original delivery path instead of silently becoming still images. Damaged/oversized input fails validation. Original authorization is checked on every derivative request, including cache hits; derivative responses remain `no-store` in browsers.

`[media] cache_bytes` defaults to 8 MiB (0 disables retention, maximum 64 MiB); `cache_entries` defaults to 128 (1–1024); `cache_seconds` defaults to 3600 (1–3600). This is a separate budget from the public response cache. Keys include the actual original byte hash, width and format; each stored entry counts its body, key, headers and entry structure. Original reads/hashing and encoding each have a separate `worker_concurrency` admission bound; large hashes run off the async request threads. Read/encode buffers and encoder allocations are additional transient costs, not part of retained-cache bytes. Cache hits reuse encoding but still read and validate original access.

## Native PostgreSQL 17 WAL recovery integration

`wal-store INPUT NAME` and `wal-restore NAME OUTPUT` are file-only helpers for PostgreSQL 17 `archive_command`/`restore_command`. They do not connect to the wpalt database, initialize a site or take the app server lock. Use the same executable and private config from the PostgreSQL operating-system account. Configure an existing independent directory, a separately held private key and the canonical cluster identifier from `SELECT system_identifier::text FROM pg_control_system()`:

```toml
[postgres_archive]
enabled = true
system_id = "REPLACE_WITH_ACTUAL_CLUSTER_IDENTIFIER"
key_file = "/private/postgres-recovery.key"
directory = "/independent/postgres-wal"
max_segment_bytes = 16777216
```

Use PostgreSQL `wal_level = replica`, `archive_mode = on` and `archive_command = '/absolute/wpalt --config /private/native.toml wal-store "%p" "%f"'`. Follow PostgreSQL's restart/privilege procedures. An identical retry verifies the existing ciphertext and succeeds; a different record at the same name fails instead of overwriting it. Records bind their filename and cluster identifier inside authenticated encryption. Full segments check PostgreSQL 17 long-header magic, byte order, source identifier, segment size and page address. Timeline/backup-history files are bounded UTF-8 records; native PostgreSQL validates their engine meaning. Partial segments are unsupported. The segment budget accepts powers of two from 1 MiB to 1 GiB, default 32 MiB; configure the actual engine size. Concurrent processes and larger configured segments have additional transient memory costs.

Retain a verified **native physical base backup**, its required continuous WAL chain, engine/version/architecture details and matching immutable media/config. Native cluster base directories are not encrypted wpalt logical packages: protect their permissions and encrypt/protect their storage independently. `pg_basebackup -X stream` and `pg_verifybackup` are PostgreSQL's operator tools. Restore into a separate empty native cluster and configure `restore_command = '/absolute/wpalt --config /private/native.toml wal-restore "%f" "%p"'`, `recovery.signal` and an explicit named/time/LSN recovery target. `wal-restore` authenticates the complete record before atomically replacing PostgreSQL's output path, including an existing recovery scratch file. Missing/wrong/tampered records return nonzero; do not treat an incomplete chain as a recovery point. Review `pg_stat_archiver`, disk space and quota alerts. Automatic native-WAL pruning is intentionally unavailable without verified base/chain coverage.

SQLite continues to use the consistent application snapshot path. A PostgreSQL physical point preserves the whole cluster, not just wpalt or media files; provision native engine privileges explicitly. Managed logical incremental snapshots remain a different mechanism. `scripts/native_pitr_acceptance.py` verifies the clean Linux executable against a digest-pinned official PostgreSQL 17 image: real base backup/manifest verification, real encrypted archiving, source cluster unavailable, named-point recovery, exclusion of a later mutation and wpalt publication/catalog delivery. It is a required release gate; results are pending until that real-engine CI journey passes. [PostgreSQL 17 archiving guidance](https://www.postgresql.org/docs/17/continuous-archiving.html) and [native header declarations](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/include/access/xlog_internal.h) checked 2026-10-04.

## Reference-aware cleanup

Operations → **Preview unused media cleanup** scans the database's complete backup table contract (including drafts, publications, revisions, themes, forms, membership and commerce records). Conservative UUID references, decoded JSON and percent-encoded URLs retain originals. Only unreferenced inventory images and safe unregistered image files are listed. The owner reviews the list before permanent removal; preserve a verified backup first. Images used only by other websites or files outside this database cannot be detected. Cleanup does not delete revisions, orders, payment history, form attachments or business records.

`wpalt --config site.toml cleanup` prints the same plan. Execute with `cleanup --execute PLAN_HASH --cutoff PLAN_CUTOFF` within ten minutes. The mutation lock protects a fresh reference/inventory check through deletion; a changed candidate set rejects the old plan. A conservative scan is capped at 100,000 rows/UUID references, 64 MiB of text and 1,000 media records/files, and refuses unsupported workloads rather than deleting from an incomplete scan. Unknown files, symlinks, unsafe names or missing registered images require manual/integrity inspection first. Expired sessions can be removed in the same transaction; live sessions are retained.

Library removal commits before file unlink. If storage fails or the process stops after commit, remaining files are inaccessible through media delivery and appear as retryable unregistered candidates in the next preview. Failed unlinks are reported individually. No atomic cross-filesystem/database deletion is claimed. One owning application process and app-controlled storage remain required; direct external database/file writers are unsupported. Deletion frees file space, while database pages may be reused internally; maintenance-window database compaction remains an operator task.

## Asset and image loading

The locked frontend build minifies bundled scripts and admin CSS. Feature scripts load on their owning surfaces; public theme widgets load only when the selected render tree needs tabs. Configure `[assets] scoped_theme_css = true` and `preload_theme_css = true` (both defaults). Template styles are generated from the header, footer, selected template and transitively used components. Unrelated templates/components are excluded; responsive and conditional branches are retained. The small selected stylesheet remains a local, synchronous stylesheet under strict `style-src 'self'`. This is deterministic critical render-tree CSS, not a claim of arbitrary above-fold CSS analysis. Base shared application styles remain conservative. Turn either control off for diagnosis; no browser-side/cloud optimizer is required. A preload immediately adjacent to its consumer may provide little benefit; measure the actual workload rather than promising faster rendering.

New images inserted through the editor read the authenticated local original in the browser and store bounded intrinsic width/height. The default is lazy loading. Select **Loading priority → Early** for an important first image: publication keeps eager/high priority and preloads at most one local `/media/UUID` image that occurs in the rendered body. No imported external image is preloaded or fetched by the server. Original media authorization remains unchanged. Dimensions are layout metadata, not an authorization decision. Composition images and imported local images without dimensions gain intrinsic dimensions in a transient render tree. One batched authorized media lookup supplies filenames/checksums; header inspection reads at most 64 KiB per original, at most 128 images (8 MiB header input) with a configured 2-MiB decoder allocation budget per inspection (decoder allocation limits are not a hard total process-memory cap) and shared bounded native workers. Metadata shares the existing bounded media cache and is keyed by immutable source identity/checksum. A busy worker, damaged/oversized header or metadata outside the inspected prefix simply leaves optional dimensions absent. External URLs are never fetched. Published historical documents are not rewritten. Studio image nodes expose Lazy/Early priority; eager/high priority uses at most one rendered local image preload across the document/composition. Shared gallery images remain lazy. Browser insertion errors are retryable and timeout after ten seconds; duplicate insertion is disabled while checking the source.

## Optional local video worker

Owners may enable `[video] enabled = true`, `ffmpeg = "/absolute/owner-installed/ffmpeg"` and `ffprobe = "/absolute/owner-installed/ffprobe"`. FFmpeg must provide libx264/AAC; the application does not download tools. Media library then offers **Process local video**, restricted to administrators and CSRF-protected. Choose public or editors-only visibility; the default is private. The processed MP4 enters the shared media inventory, checksum/integrity, cleanup and fresh recovery workflows. The source is a private temporary processing file and is removed afterwards. Outputs are not automatically published into content, and captions/subtitles are not carried over: owners must provide an accessible presentation/caption workflow for their video. Images remain the content editor's image picker; videos have their own open/play controls.

CLI: `wpalt --config site.toml video-transcode SOURCE OUTPUT`. Creates a new private output file without replacing an existing file. It uses the same processing profile but does not add that output to the library automatically.

The fixed profile accepts local MP4/WebM with known duration at most two minutes, up to eight streams, maximum source frame 1920×1080 and source bytes at most the smaller of `max_upload_bytes` and 32 MiB. It scales down to fit 1280×720, 30 fps, H.264/AAC MP4, removes metadata/chapters and excludes non-selected streams. One decoder/encoder/filter thread is requested and the shared media semaphore bounds admitted workers. Inspection has a three-second deadline and encoding twenty seconds; timeout/drop kills the child. Network protocols and playlist input formats are excluded; filenames/arguments are generated rather than supplied as shell code. Output is capped at 32 MiB and outputs reaching the cap are rejected. Private temporary directories are removed on completion/error/cancellation; abrupt host termination may leave a `.video-UUID` directory for owner inspection, never a served output.

`-max_alloc` limits individual FFmpeg allocations, **not total native process memory**. Owner-installed codec software runs with the host user's privileges; protocol/format restrictions are not an OS sandbox against decoder vulnerabilities or all malicious local-file behaviors. Run the tools/application under a restricted host account with OS memory/CPU/storage quotas and an isolated filesystem when accepting untrusted video. Keep codec security updates current. Source probes and fixed conversion cannot guarantee a safe decoder for every hostile input. This optional module is disabled by default and adds no worker/background work when disabled. MP4 delivery currently streams bounded complete files; no adaptive streaming/range-seek guarantee is claimed.

## Local role and region variants

`[variants] role_variants = true` enables current server-validated role buckets for the narrow public cache allowlist. Role labels are revalidated under the mutation lock before a hit, then keyed separately from region and URL/query. Every private/protected route keeps its existing current authorization and `no-store` policy. Role buckets are presentation, not permission checks or paid-entitlement caches. Shared entries never include user names/IDs, carts, session capabilities or arbitrary personal fields. A sole valid `wpalt_session` cookie may use the role bucket; any additional cookie, authorization/range/conditional header or existing private-cache response still bypasses storage. Disabled/expired sessions cannot select their previous role bucket.

Owner-defined `[[variants.region_networks]] network = "192.0.2.0/24"` and `region = "local-east"` entries map the **native connection peer** to up to 64 named regions; IPv6 CIDR is supported. First matching network wins, otherwise `unknown`. This is local owner-provided geographic/network data, not a country-location database. Supplied forwarded-IP, role and region headers cannot select buckets. Behind a reverse proxy, the native peer is the proxy and this configuration cannot infer the visitor's region. Trusted-proxy geolocation needs a separately verified topology protocol; do not treat an arbitrary forwarded header as authority.

Public composition bindings `site.role` and `site.region` can drive text and existing conditional presentation. Home/search/publication contexts receive the same validated labels. Draft previews use their normal content contract, and label-dependent presentation does not grant access to protected content or media. Both settings add bounded work only when configured; authenticated role classification adds indexed session/user lookup cost. Region/role buckets share the existing global cache byte/entry limits, so enabling more variants cannot create an unbounded per-variant cache.


## Background history and retries

Operations shows the latest eight scheduler cycles and their stage outcomes; `wpalt job-history` prints the retained 64-cycle private history while the server is stopped. Each cycle durably publishes an intent before polling recovery, publication, campaigns, commerce, mail and retention. Completion records success/failure, processed counts where available and monotonic durations. Recovery/retention stages omit counts because those workers have no count contract. Displayed times explicitly use UTC. Error strings, recipients, credentials and payloads are excluded. History is capped at 128 KiB, atomic private file replacement with sync; at most two history writes per scheduler cycle, with the existing configured 1–3600 second poll interval. Slow work skips missed timer ticks and never overlaps the next cycle.

Cancellation or host loss can leave a `running` intent without an outcome. The next cycle marks it `interrupted`; this does not prove that no stage committed. If final history persistence fails, an error diagnostic calls for inspecting site storage and individual feature state. Intent persistence failure blocks the entire cycle before domain work. Journal state never dispatches retries: existing publication, billing/payment and outbox state machines govern the next poll. Provider delivery interrupted after remote acceptance still has the documented ambiguous-delivery boundary. Native blocking file sync retains its separate I/O lock even when the async caller is cancelled, preventing a later cycle from racing an unfinished atomic publication.

This host-local maintenance history survives restart; it is not a financial ledger, long-term archive or a recovery replay queue. Full logical packages retain domain/outbox state and privileged audit events, but do not transplant old host scheduler history into a fresh host. Preserve the private file separately for long-term diagnostics if needed.


## Browser hardening controls

`[headers]` controls compile once when the application starts; each response clones the prepared values, including cache hits and failures. Supported controls:

```toml
[headers]
referrer = "strict-origin-when-cross-origin" # or same-origin / no-referrer
hsts_seconds = 31536000                     # 0 disables an existing policy over HTTPS
hsts_include_subdomains = false
isolate_opener = true
same_origin_resources = false              # true also restricts public hotlinking
upgrade_insecure_requests = false          # effective only for configured HTTPS
```

HSTS is emitted only for a configured HTTPS `base_url`; forwarded-protocol headers do not activate it. TLS termination is operator-owned. Before including subdomains, ensure every affected subdomain supports HTTPS; a browser can retain an HSTS policy after configuration changes until it receives a new HTTPS policy or the previous lifetime expires. No automatic browser preload-list submission occurs. Opener isolation defaults to `same-origin` and is independently configurable for owner integrations. Sensitive account/admin/member/commerce surfaces use same-origin resource policy; public resources remain shareable unless the owner enables the stricter public policy. Token-bearing confirmation/registration/identity/gift routes always retain `no-referrer` regardless of the general choice.

Strict same-origin script/style CSP, object/base restrictions, frame restrictions, `nosniff` and camera/microphone/geolocation denial remain mandatory. Preview documents permit only same-origin framing, disable scripts and prohibit live form submission. Public form embedding retains its existing same-origin frame contract. There is no arbitrary CSP string editor, inline/eval allowance or insecure wildcard switch. HSTS may range from 0 to two years; unsafe/unknown settings fail configuration validation. Operations exposes effective controls; `show-config` includes the same redacted structured configuration.


Video upload progressively enhances the native form with an inline processing state, duplicate-submit guard and retry that retains the selected source. A lost connection directs the owner to inspect the library before retry, because processing may already have committed. Library previews start muted for a quiet owner workspace, remain keyboard/native-control accessible and fit narrow screens. This is an owner media-preview workflow; captions/public video authoring are not delivered by this worker. Long processing revalidates the current session/role/CSRF under the write boundary before media publication; role/session revocation wins after a previously authorized processing start. Image upload and media detail edits use the same current-authority check at their commit boundary. Debug diagnostics expose bounded source/output sizes and processing durations without filenames, payloads or credentials.

The real native browser fixture generates a silent local MP4, rejects damaged input without adding inventory, measures error/busy/populated states at 320/768/1440 with text spacing and accessibility, actually decodes/plays output, excludes it from image pickers and verifies publication then revocation. Optional FFmpeg is installed only in CI fixture jobs; release packages do not contain or install codecs. Backend journeys also cover worker saturation, credential revocation during admitted native processing, checksum-identical private fresh recovery and temporary workspace removal. These tests establish the implemented bounds/workflows, not an OS sandbox or a malware-free decoder guarantee.

## Declared local optional scripts

An owner may configure up to eight reviewed UTF-8 analytics scripts under `[[consent_scripts.scripts]]`, each with `id`, `label`, `purpose`, absolute `path` and lowercase `sha256`. Each file is at most 256 KiB and combined source at most 1 MiB. Startup rejects symlinks, missing/damaged/checksum-mismatched files. Source is pinned in memory; restart with a reviewed checksum to deploy a change. Disabled/empty configuration allocates no source bytes and downloads no optional script. There is no vendor account or outside download.

Enable analytics in Engagement and declare its purpose. Visitors see every script's label and purpose before the explicitly labeled grant. A full SHA-256 manifest binds their durable consent record to identifiers, source checksums and declared purposes. Changed code or purpose requires renewed consent even if the numeric analytics policy did not change. A stale client cannot grant an outdated manifest. The same binding governs capture, promotions and protected source reads; GPC/configured DNT prevents all of them. Responses are same-origin and `no-store`; a valid prior download does not authorize a later read after withdrawal. Fresh recovery retains the grant only when the independently supplied, reviewed local script configuration matches. Script files/paths are owner-managed executable dependencies, not media or automatic recovery payloads.

Scripts execute with the website page's JavaScript privileges. CSP stays restricted to own-origin resources and no inline/eval exception is added, but this is **not** a sandbox for malicious owner code or a generic third-party tag manager. Use reviewed scripts without undeclared personal-data persistence; the owner remains responsible for their behavior and any independent data erasure. This initial workflow groups declared scripts with analytics rather than claiming a full multi-category consent-management product or legal compliance certification. Withdrawing consent erases the visitor's local analytics record and reloads a page containing optional code to unload it; same-origin open tabs receive a withdrawal message. Source retrieval is reauthorized by the server. Already transmitted data and arbitrary script-owned storage cannot be retroactively revoked by a banner.

Example (replace source checksum with the actual reviewed digest):

```toml
[[consent_scripts.scripts]]
id = "local-analytics"
label = "Local analytics helper"
purpose = "Measure consented visits on this server."
path = "/srv/wpalt-scripts/analytics.js"
sha256 = "<64 lowercase hexadecimal characters>"
```

Source guidance reviewed 2026-10-05: [W3C CSP3](https://www.w3.org/TR/CSP3/) (current working draft; not a final conformance certificate), [Global Privacy Control](https://www.w3.org/TR/gpc/) and [HTTP cache control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control). Full manifest binding, file budgets and owner-code trust boundaries are engineering policy.

## Verified account data requests

`/account` links to **Data and privacy**. A signed-in local account proves its current password to download its explicitly allowlisted account-linked JSON or submit access/erasure review. Source authorization is checked again after password verification and before work; CSRF and origin controls apply. Exports include identity, authored current content, member profile/access/groups/progress/attempts/assignments/certificates/discussions, claimed gifts/referrals/commissions, carts/purchases/lines/payments/refunds/subscriptions/payouts and request outcomes. They exclude credentials, tokens, provider payloads, unrelated accounts and automatically inferred ownership of anonymous forms or visitor cookies. The export names its additional review boundaries. This is an account-linked export, not a claim that arbitrary plugin/theme fields or every independent system's personal data can be discovered automatically.

The owner follows **Review data requests** in Operations, opens the paginated queue and records a fulfilled, partial or refused outcome with a clear requester-visible response. The requester reviews their local history; no mail provider is required. Retention reasons, independently verified anonymous data and separate deletion/export actions must be explained. Recording a decision does not perform automatic erasure. A separate, explicitly confirmed **Remove account identity and profile** action atomically disables sign-in, replaces name/email with a pseudonymous local identity, destroys the usable password and sessions/factors/passkeys/linked identities, removes profile biography and records a partial outcome. Stable subject IDs remain intact. The last owner cannot be removed. Financial/customer records, authored content, audience/forms and independent backups still require explained separate handling; this action never claims whole-site erasure. The owner must communicate the result through an independently verified channel because the removed account can no longer sign in. Existing profile, audience, user/access and form controls remain the means of handling records; financial identity, payment/delivery graphs and independent recovery copies must not be indiscriminately deleted or replayed. An erasure request is not declared fulfilled automatically. Account requests preserve their subject and outcomes through fresh recovery. Anonymous/non-account people must contact the owner for separately verified handling. This is a defined local workflow, not legal compliance certification.

`[privacy]` controls `max_requests` (default 10,000), `requests_per_account` (50), `export_group_records` (1,000) and `export_bytes` (4 MiB). One pending request per account/type is enforced by a partial unique index; retrying returns to the existing request. Quota exhaustion refuses admission explicitly without discarding an existing request. Owner and account history pages remain bounded and navigable. Export uses indexed subject predicates, bounded streaming and a consistent transaction; excess data fails explicitly instead of returning an apparently complete truncated archive. Host owners can use `wpalt privacy-export USER_UUID NEW_FILE` offline with the same allowlist/budgets. The command writes a new private file and logs its action class without argv or exported data.

Schema 10→11 is an additive transaction, with queue indexes and subject indexes for exports. Preview v10 archives require their matching binary to restore into a fresh target, then the current executable to migrate/re-export; there is no v10 runtime parser. `migrate-backup` remains the dedicated meaningful M6 conversion and now includes an empty privacy queue. Current recovery validates subjects, duplicate/open identities, states, responses and timestamps before target writes.

Reference reviewed 2026-10-05: [WordPress privacy workflow](https://wordpress.org/documentation/article/wordpress-privacy/) and [WordPress erasure callbacks](https://developer.wordpress.org/plugins/privacy/adding-the-personal-data-eraser-to-your-plugin/). wpalt's password-proven local workflow and conservative financial retention boundaries are explicit engineering decisions; it does not implement WordPress's email confirmation mechanism or callback API.

## Editorial selection and URL-aware held clones (introduced in native schema 12)

Use `recovery-select INPUT --post CONTENT_UUID [--post ANOTHER_UUID] [--key-file KEY]` for a portable preview. Inspect retained/omitted UUIDs and per-table counts. Repeat with `--execute PLAN --output NEW_PRIVATE_PACKAGE` to create exactly that validated package. It retains the shared account/access/learning/financial/workflow graph and all media; it is not a personal-data reduction tool. References and translation dependencies can retain additional posts. Ordinary restore requires a fresh empty target. Scan budgets fail explicitly; no partial output is accepted.

Use the destination config with `recovery-clone INPUT --source-origin https://old.example [--key-file KEY]` to preview a URL-aware clone. Repeat with `--execute PLAN --output NEW_PRIVATE_PACKAGE`; restore that package on the destination. Allowlisted presentation fields are rewritten; immutable financial/customer history, queues, forms, external identities and optional script files require manual review. Source sessions are excluded and passkeys are removed. Target canonical URLs derive from target config. HTTPS/password/TOTP safeguards remain applicable.

A restored clone is durably held read-only. Password login/logout and inspection work; HTTP mutations/payment webhooks/external identity callbacks and background cycles remain blocked across restart and subsequent recovery. Operations explains the hold. With the server stopped, after reviewing source shutdown, delivery queues, external payment ownership, identities and credentials, run `clone-activate --review 'Detailed actual review and retained precautions…'`. The new target origin must match. Activation is audited and is an explicit operator decision, not proof that payment-provider ownership or uncertain mail outcomes have transferred. Keep staging clones held and provider credentials disabled. Do not run two active sites against the same external subscriptions/queues.

The dedicated M6 converter produces the current v13 graph. See [ADR 0011](decisions/0011-selective-recovery-held-clones.md).
