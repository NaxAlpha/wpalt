User-facing outcome: compose and operate a responsive multi-template site through one admin builder, with reusable components/layouts/tokens, typed content models/relationships/repeaters/options, dynamic bindings/listing/conditions, safe theme draft/preview/publish/revert/switch and portable packages. A JSON-only endpoint or renamed basic blocks is not completion.

Implementation direction:
- Rust remains the rendering/validation/permission authority. A bundled Preact admin island (locked npm/esbuild dev dependencies) powers the visual outline/properties/preview experience; no Node or network needed at runtime. Existing publishing/admin forms remain usable.
- Add cohesive schema and theme modules and a dedicated builder HTTP module; keep web.rs from absorbing another monolith.
- Theme packages are versioned bounded declarative JSON, not PHP/JS/executable templates: nodes, reusable components, template selection, responsive layout, design tokens, text/link/image/Markdown/navigation/list/repeater/conditions/native accessible widgets. Component parameters are explicit. No eval, arbitrary filesystem/network, freeform attribute/event injection or unbounded recursion.
- Server validation checks allowed binding roots/paths, references, component cycles, depth/node/expanded render work/query limits, safe URLs/media, token/style ranges, meaningful HTML semantics, theme/schema dependencies. Rendering uses the exact same engine for preview/live and escapes data; Markdown remains sanitized.
- Gather content/relationship/media dependencies in bounded bulk queries, select published snapshots for public requests, keep draft-only related data out of visitor output. No per-item query expansion. Request-local data resolution plus publication-version keyed immutable compiled theme cache; invalidate immediately after publish/activate/options changes. Do not keep obsolete packages active just for cache compatibility.
- Theme draft/version/live snapshot/revisions are transactional with optimistic concurrency. Autosave changes draft and refreshes an authenticated sandboxed iframe preview only; explicit publish/activate controls visitor output. Restore creates a new working draft and never silently changes the live theme. Admin-only design/schema/options writes; editor content/preview permissions remain intact.
- Typed schemas provide primitives plus media, relationships, objects/repeaters/galleries/reusable groups and custom content types. Shared options use the same field definitions. Authoring widgets validate structure and show useful errors. Data-bearing schema edits must not silently invalidate/discard existing content.
- Schema 2 uses one-off M1 data migration (preserve content/settings/users/media), no schema-1 runtime parsing branch. SQLite constraint changes use the documented recreate/copy/check transaction; PostgreSQL uses its constraints/DDL. Backup restores current schema only; M1 backups need restore with M1 then upgrade, or a documented disposable reset. Current snapshot covers new theme/schema/options state.
- CLI theme import/export/install/publish controls align with admin; package portability states media/schema dependencies rather than hiding unresolved references.

Migration detail: the M1 SQLite posts/settings/terms CHECK constraints prevent custom kinds/themes/taxonomies. Use one acquired connection with foreign_keys disabled before the transaction, create/copy/drop/rename tables without first renaming originals, rebuild indexes/triggers, foreign_key_check before commit, then re-enable foreign_keys even on error. PostgreSQL drops named constraints transactionally. All changes are schema-version guarded; later schema mismatch still fails. Root settings field_schema evolves into the restricted field grammar via a one-off conversion, not a permanent legacy parser. Never create built-in theme rows on every empty App::open, as that would make restore reject the target; initialize them with site initialization or data-bearing migration.

Draft previews should use the same server renderer. Prefer authenticated iframe navigation to stored valid draft revisions after autosave, sandbox without theme script execution. Preview CSP allows only same-origin frame ancestors; other admin pages remain unframeable. Generated live theme styles served through a versioned owner route, not arbitrary inline CSS/eval. Invalid edits stay local with actionable errors and cannot overwrite the last valid stored draft. Public lookup always uses current published theme/version and snapshots.

Typed-schema detail: common fields plus reusable field groups; model-specific fields plus arbitrary taxonomy definitions. Field kinds string/number/boolean/media/relationship/object/group/repeater/gallery/flexible, with bounded nesting, required flags and validated relationship targets. A flexible section references a declared variant/group. Repeater/galleries cap row/item counts. Custom taxonomy terms use the existing draft/live join separation after removing M1-only kind checks. Existing core categories/tags remain supported user capabilities. Schema edits preflight meaningful current content and live theme binding dependencies; avoid silent invalidation/data loss.

Theme style routes must account for publish races: old public HTML can still request its stylesheet just after a new publication. Keep a bounded number of published revision styles (at least the last two), serve only published revision styles publicly, and keep draft styles authenticated/no-store. This is immutable publication history, not a legacy format compatibility layer. Compiled theme cache must be bounded by installed-theme/version limits and never cache rendered private data.

Further integrity rules: disallow prototype-related identifiers (`__proto__`, `constructor`, `prototype`) throughout schema/component/parameter IDs; client state uses own-property lookups. Keep shared option draft/live snapshots separate, with explicit publication and optimistic version checks; theme previews may use draft options but visitors only see published options. Public theme activation must not silently publish unrelated option drafts. Model/common-schema edits preflight both working/live content and active-theme bindings. Existing M1 basic blocks remain a supported content primitive, not a legacy-version parser.

Core M2 gains should be concrete: one typed definition feeds structured authoring and template binding; reusable components support explicit parameters rather than copied markup; relational/repeater rendering is budgeted and bulk-resolved; one server renderer powers responsive preview and public output; themes/options have safe versions/publication state. Do not claim WordPress lacks features already present in current block bindings/theme.json.
